# N+1 개선 전/후 성능 테스트 설계

> [N+1_개선_설계.md](N+1_개선_설계.md)의 개선을 적용하기 **전과 후**를 동일 환경·동일 데이터에서 측정해
> "쿼리 수 감소"와 "응답 시간 개선"을 수치로 검증하기 위한 테스트 설계.
> 기존 폴링/SSE 측정([성능테스트_결과.md](성능테스트_결과.md))의 인프라·방법론을 재사용한다.

---

## 1. 목적과 가설

| 가설 | 내용 | 검증 지표 |
|---|---|---|
| H1 | 개선 후 요청당 DB 쿼리 수가 **방 수와 무관한 상수(2개)** 가 된다 | Com_select 델타 ÷ 요청 수 |
| H2 | 쿼리 수 감소로 응답 시간이 개선된다 | 요청별 응답 시간 p50/p95 |
| H3 | 방 수가 클수록 개선 폭이 커진다 (before는 선형 증가, after는 평탄) | 방 수별 시나리오 비교 |

---

## 2. 측정 대상

- **엔드포인트**: `GET /subjects/1/chats/rooms` — `RestChatServiceImpl.findAllById` 경로 (N+1이 발생하는 유일한 경로)
- **부하 형태**: **단일 사용자의 순차 호출**
  - 동시성 효과를 배제하고 "요청 1건의 비용(쿼리 수 → 응답 시간)"만 측정하기 위함.
  - 동시 사용자 시나리오는 이번 측정 범위에서 제외 (기존 측정 문서와 동일하게 변수를 최소화).
- **테스트 사용자**: `aaaa` (member 1) — 방 N개를 보유하도록 시드.

---

## 3. 측정 지표와 방법

### 3-1. DB 쿼리 수/요청 (핵심 지표 ①)

기존 측정과 동일하게 MySQL 누적 카운터 델타 방식 사용:

```
요청당 쿼리 수 = (측정 종료 시 Com_select - 측정 시작 시 Com_select) ÷ 완료 요청 수
```

- `SHOW GLOBAL STATUS LIKE 'Com_select'` — SELECT 쿼리만 카운트.
- N+1 여부의 **직접 증거**: before는 방 수에 비례, after는 2 고정.

### 3-2. 응답 시간 (핵심 지표 ②)

신규 부하 스크립트 `load-gen/rooms.mjs` (5장)로 요청별 응답 시간 측정:

- warmup 20회 후 200회 측정 → 평균 / p50 / p95 / max 산출.
- 순차 호출이므로 p95 = 요청당 비용의 분포 (쿼리 수가 많을수록 응답 시간이 커지고 분산도 커짐).

### 3-3. CPU / 메모리 (참고 지표)

- `docker stats --no-stream` 2초 간격 샘플링 — 기존 `scripts/measure.sh`의 샘플링 루프 재사용.
- 절대 CPU%는 환경 의존이므로 **감소율(상대값)** 관점에서만 참고.

## 4. 테스트 데이터 설계

### 4-1. 시드 정책

- **통제를 위해 채팅 테이블을 초기화한 뒤 방 N개만 시드** — data.sql의 기본 방 8개도 함께 지워서 "테스트 사용자의 방 수 = N"으로 정확히 통제.
- 대상 사용자: member 1 (`aaaa`). 상대방: member 2~10 순환 (prepare-db.sh 실행 후 10명 모두 존재).
- 방당 메시지 M개 — sender 교대, `created_at`은 방 내에서 순증가하도록 생성.

### 4-2. 시드 스크립트: `scripts/seed-chat-data.sh` (신규)

```bash
#!/usr/bin/env bash
# 채팅 데이터 시드: member 1(aaaa) 기준 방 N개(상대 = member 2..10 순환), 방당 메시지 M개
# 주의: chat_* 테이블을 초기화하므로 data.sql 기본 시드 방도 지워짐 (방 수 통제 목적)
# 사용법: ./scripts/seed-chat-data.sh [방수=100] [방당메시지=10]
set -euo pipefail
cd "$(dirname "$0")/.."

ROOMS="${1:-100}"
MSGS="${2:-10}"
MYSQL="docker exec -i noteu-mysql mysql -unoteu -pnoteu noteu"

{
  # FK 순서 고려 삭제: 메시지 → 참가자 → 방
  echo "DELETE FROM chat_message;"
  echo "DELETE FROM chat_participant;"
  echo "DELETE FROM chat_room;"

  for ((r = 1; r <= ROOMS; r++)); do
    friend=$(( (r % 9) + 2 ))   # member 2..10 순환

    echo "INSERT INTO chat_room (created_at, modified_at, subject_id) VALUES (NOW() - INTERVAL ${ROOMS} DAY + INTERVAL ${r} MINUTE, NOW() - INTERVAL ${ROOMS} DAY + INTERVAL ${r} MINUTE, 1);"
    echo "SET @rid := LAST_INSERT_ID();"   # 방금 넣은 방 id 캡처 (단일 세션이므로 유효)
    echo "INSERT INTO chat_participant (created_at, modified_at, chat_room_id, member_id) VALUES (NOW(), NOW(), @rid, 1), (NOW(), NOW(), @rid, ${friend});"

    for ((m = 1; m <= MSGS; m++)); do
      if (( m % 2 == 0 )); then sender="${friend}"; sender_name="friend"; else sender="1"; sender_name="aaaa"; fi
      echo "INSERT INTO chat_message (created_at, modified_at, room_id, sender_id, sender_name, message) VALUES (NOW() - INTERVAL ${MSGS} MINUTE + INTERVAL ${m} MINUTE + INTERVAL ${r} SECOND, NOW(), @rid, ${sender}, '${sender_name}', CONCAT('seed r${r}-m${m}'));"
    done
  done
} | $MYSQL

echo "시드 완료: 방 ${ROOMS}개 × 방당 메시지 ${MSGS}개 (member 1 기준)"
```

### 4-3. 시나리오 행렬

| 시나리오 | 방 수 (N) | 방당 메시지 | before 예상 쿼리/요청 | 2쿼리안 예상 | 1쿼리안 예상 |
|---|---|---|---|---|---|
| S1 | 10 | 5 | ~22 (2N+2) | 2 | 1 |
| S2 | 50 | 10 | ~102 | 2 | 1 |
| S3 | 100 | 10 | ~202 | 2 | 1 |
| S4 | 200 | 10 | ~402 | 2 | 1 |

- before = **2N + 2** (목록 1 + subject EAGER 1 + 방마다 마지막 메시지 1 + 방마다 참가자 1) — 2026-08-25 로그 관측(방 10개 → 22회)으로 확인된 수식. Com_select 측정으로 재확인한다.
- **2쿼리안 vs 1쿼리안 비교가 이 테스트의 핵심** — 쿼리 수뿐 아니라 p95 응답시간으로 실제 우위를 판정한다. 1쿼리안이 "진짜 1개"가 되려면 참가자까지 fetch join에 포함해야 한다 (개선설계 5장 — 구현 후 로그 검증 필수).

## 5. 부하 스크립트: `load-gen/rooms.mjs` (신규)

기존 `login.mjs`가 만든 `sessions.json`을 재사용. 의존성 없이 내장 fetch만 사용.

```js
// load-gen/rooms.mjs — 방 목록 API 응답시간 측정 (N+1 전/후 비교용)
// 단일 세션 순차 호출: 동시성 효과를 배제하고 요청당 비용(쿼리 수 → 응답시간)만 측정
// 사용법: node rooms.mjs [username=aaaa] [요청수=200] [warmup=20]
import { readFileSync } from 'node:fs';

const BASE = process.env.BASE_URL ?? 'http://localhost:8080';
const USERNAME = process.argv[2] ?? 'aaaa';
const REQUESTS = Number(process.argv[3] ?? 200);
const WARMUP = Number(process.argv[4] ?? 20);

const sessions = JSON.parse(readFileSync(new URL('./sessions.json', import.meta.url), 'utf8'));
const session = sessions.find((s) => s.username === USERNAME);
if (!session) {
  console.error(`sessions.json에 '${USERNAME}' 없음 — login.mjs 먼저 실행`);
  process.exit(1);
}

const times = [];
let errors = 0;

for (let i = 0; i < WARMUP + REQUESTS; i++) {
  const t0 = performance.now();
  try {
    const res = await fetch(`${BASE}/subjects/1/chats/rooms`, {
      headers: { cookie: session.cookie },
    });
    await res.text(); // 응답 본문 소비 (커넥션 재사용 위해)
    if (!res.ok) { errors++; continue; }
    if (i >= WARMUP) times.push(performance.now() - t0);
  } catch {
    errors++;
  }
}

const sorted = [...times].sort((a, b) => a - b);
const q = (p) => (sorted.length
  ? sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))].toFixed(1)
  : 'n/a');
const avg = times.length ? times.reduce((a, b) => a + b, 0) / times.length : 0;

console.log(JSON.stringify({
  user: USERNAME,
  requests: times.length,
  errors,
  avgMs: avg.toFixed(1),
  p50: q(0.5),
  p95: q(0.95),
  maxMs: sorted.length ? sorted.at(-1).toFixed(1) : 'n/a',
}, null, 2));
```

## 6. 측정 오케스트레이션: `scripts/measure-n1.sh` (신규)

시드 → (Com_select 델타 + rooms.mjs) 반복 측정까지 한 번에 수행.

```bash
#!/usr/bin/env bash
# N+1 전/후 측정: 시드 후 rooms.mjs를 R회 반복하며 Com_select 델타로 쿼리/요청 산출
# 사용법: ./scripts/measure-n1.sh [방수=100] [방당메시지=10] [요청수=200] [반복=3]
set -euo pipefail
cd "$(dirname "$0")/.."

ROOMS="${1:-100}"
MSGS="${2:-10}"
REQUESTS="${3:-200}"
REPEAT="${4:-3}"

mysql_q() { docker exec noteu-mysql mysql -unoteu -pnoteu noteu -N -e "$1" 2>/dev/null; }

echo "== 시드: 방 ${ROOMS}개 × 방당 메시지 ${MSGS}개 =="
./scripts/seed-chat-data.sh "$ROOMS" "$MSGS"

for i in $(seq 1 "$REPEAT"); do
  echo ""
  echo "=== 측정 ${i}/${REPEAT} (요청 ${REQUESTS}회, warmup 20회) ==="

  select_start=$(mysql_q "SHOW GLOBAL STATUS LIKE 'Com_select'" | awk '{print $2}')
  node load-gen/rooms.mjs aaaa "$REQUESTS" 20
  select_end=$(mysql_q "SHOW GLOBAL STATUS LIKE 'Com_select'" | awk '{print $2}')

  awk "BEGIN{printf \"쿼리/요청: %.1f\n\", ($select_end - $select_start) / $REQUESTS}"
done
```

- 응답 시간(avg/p50/p95)은 `rooms.mjs`가 직접 출력.
- **주의**: before 측정(방 200개)은 요청당 쿼리가 수백 회라 200요청에 수십 초가 걸릴 수 있다. 총 측정 시간이 60초를 크게 넘으면 `요청수`를 50~100으로 줄인다. 전/후에 **같은 요청수**만 유지하면 된다.

## 7. 실험 절차

### 7-1. Before 측정 (현재 코드 그대로)

```bash

# 2. 테스트 유저 준비 + 로그인 세션

# 3. 시나리오별 측정 (예: 방 100개 × 메시지 10개, 3회 반복)

```

시나리오별 결과를 8장 템플릿에 기록.

### 7-2. After 측정 (2쿼리안 — fetch join + 서브쿼리 일괄 조회)

```bash
# 1. [N+1_개선_설계.md](N+1_개선_설계.md) 4장의 변경 적용 → 서버 재기동
docker compose up --build -d

# ⚠️ ddl-auto: create 로 DB가 초기화된다 → 2~3단계 재실행 필수
./scripts/prepare-db.sh
node load-gen/login.mjs

# 2. 동일한 시드, 동일한 요청수로 측정 (before와 명령어 동일)
./scripts/measure-n1.sh 100 10 200 3
```

### 7-3. After 측정 (1쿼리안 — 자기 조인 + fetch join + Tuple)

```bash
# 1. 개선설계 5장의 1쿼리안으로 교체 → 서버 재기동
#    (변형 간 전환은 git 커밋을 활용: 2쿼리안 커밋 → 1쿼리안 커밋 → 필요 시 checkout)
docker compose up --build -d
./scripts/prepare-db.sh
node load-gen/login.mjs

# 2. 동일 측정 + 반드시 "쿼리/요청 = 1"인지 확인 (참가자 lazy load가 남으면 1+N이 됨)
./scripts/measure-n1.sh 100 10 200 3
```

- 1쿼리안이 "진짜 1쿼리"가 되려면 참가자·과목이 같은 쿼리의 fetch join에 포함되어야 한다. 구현 후 SQL 로그로 쿼리 1개만 나가는지 확인하는 것이 이 단계의 첫 관문.

### 7-4. 방 수별 반복 (H3 검증, 선택)

```bash
for n in 10 50 100 200; do
  ./scripts/measure-n1.sh $n 10 200 3
done
```

- 방 수를 바꿀 때마다 `seed-chat-data.sh`가 테이블을 초기화하고 재시드하므로 **앱 재기동 불필요** (시드 스크립트가 멱등).

### 7-4. 통제 조건

| 항목 | 규칙 |
|---|---|
| 측정 중 다른 부하 금지 | 각 시나리오가 측정 윈도우 안에서 폐쇄적이어야 함 (기존 측정과 동일) |
| `show_sql` 비활성 | 로그 I/O가 응답 시간을 오염시킴 — 측정 시엔 `format_sql: false` 유지. show_sql은 **개발 검증 단계에서만** 임시 사용 |
| 앱 재기동 주의 | 재기동하면 DB 리셋 → prepare-db → login → seed 순서 재실행 |
| 반복 측정 | 시나리오당 3회, 평균 기록 — 단발 측정의 노이즈 제거 |
| 전/후 동일성 | 시드 파라미터(방수/메시지수)와 요청수가 전/후 동일해야 비교 가능 |

| # | 기준 | 통과 조건 |

## 9. 이력서 반영 문구 (수치 템플릿)

> - **상황**: 채팅방 목록 조회 API가 방마다 개별 쿼리를 실행해, 사용자의 방 수에 비례해 DB 쿼리가 선형 증가하는 N+1 문제 발생
> - **행동**: 집계 서브쿼리의 JPQL 제약을 우회해 방별 최신 메시지를 일괄 조회하고, 참가자 fetch join을 적용
> - **성과**: 방 100개 기준 요청당 DB 쿼리 202회 → 2회, p95 응답시간 33.3ms → ___ms (약 ___% 단축, 로컬 docker 부하테스트 기준)

### 면접에서 먼저 말할 한계

- 로컬 docker(1코어) 측정 — 절대값이 아니라 **감소율·쿼리 수(구조적 수치)** 기준으로 설명.
- 단일 사용자 순차 호출 기준 — 동시성 시나리오는 미측정.
- 쿼리 수는 구조상 방 수와 무관한 값이므로 환경에 덜 민감한 지표다 (강조 포인트).
- 1쿼리안이 p95에서 확실한 우위를 보이면 성과 문구의 "2개"를 "1개"로 교체 — 어느 쪽이든 측정값 기준으로 작성.
