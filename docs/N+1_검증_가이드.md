## 3. 결론: 목표대로 "2쿼리" 달성 (이전 "3쿼리 확정" 결론은 철회)

설계 문서(N+1_개선_설계.md) 4장의 목표는 "2쿼리 고정"이었고, 실제로 달성했다.

한동안 `Member.role`이 `@ElementCollection(fetch = EAGER)`라 3쿼리로 확정했었지만, 그 근거였던
"QueryDSL로 `member.role`을 fetch join할 수 없다"는 판단이 **틀렸다**. 별칭을 만들려 했던 것이 문제였고,
fetch join에는 별칭이 필요 없다:

```java
.join(chatParticipant.member, member).fetchJoin()
.leftJoin(member.role).fetchJoin()      // → HQL: left join fetch member.role
```

`ChatRoom.participants`가 `Set`이라 백(bag)이 `Member.role` 하나뿐이어서 `MultipleBagFetchException`도 걸리지 않는다.
상세는 4장 이슈 2 참고. MySQL general_log로 요청당 SQL이 정확히 2건임을 확인했다.

## 4. 알려진 이슈 상세 (히스토리)

### 이슈 1: MySQL 3065 — SQL DISTINCT + ORDER BY (해결됨)

- **증상**: `java.sql.SQLException: Expression #1 of ORDER BY clause is not in SELECT list ... incompatible with DISTINCT`
- **원인**: fetch join 쿼리에 `.distinct()`를 붙이면 Hibernate가 `SELECT DISTINCT`를 SQL에 통과시킴. 정렬용 `leftJoin(chatMessage)`의 `created_at`이 SELECT 목록에 없어 MySQL이 거부.
- **해결**: `.distinct()` 제거 → `fetch().stream().distinct().toList()`로 Java에서 중복 제거.

### 이슈 2: `member_role` 2차 쿼리 (해결됨 — 이전 "해결 불가" 결론은 오진단이었음)

- **증상**: 요청당 +1쿼리. `select r1_0.member_id, r1_0.role from member_role r1_0 where r1_0.member_id=1` — 로그인 멤버 1회, 방 수와 무관한 상수.
- **원인**: `Member.role`이 `@ElementCollection(fetch = FetchType.EAGER)`(`Member.java:41-42`). fetch join으로 하이드레이션된 member의 EAGER 컬렉션을 Hibernate가 2차 select로 로딩.
- **해결**: `.leftJoin(member.role).fetchJoin()` — **별칭 없이** 컬렉션 경로를 그대로 조인하면 된다.

```java
.join(chatParticipant.member, member).fetchJoin()
.leftJoin(member.role).fetchJoin()          // → HQL: left join fetch member.role
```

- **왜 이전 결론이 틀렸나**: 두 시행착오 모두 *별칭을 만들려고* 한 것이 문제였다. fetch join에는 별칭이 필요 없다.
  - `new EnumPath<Role>(Role.class, "memberRole")` — 별칭 생성 시도. 생성자가 protected라 컴파일 실패한 것은 맞지만, **애초에 필요 없는 코드**였다.
  - `member.role.any()` — `any()`는 조인 대상이 아니라 조건절용이라 별칭으로 쓸 수 없다.
  - `QMember.role`은 `ListPath<Role, EnumPath<Role>>`, 즉 `CollectionExpression`이므로 `leftJoin(CollectionExpression)` 오버로드에 그대로 들어간다. 별칭 인자가 없는 형태가 존재한다.
- **`MultipleBagFetchException`은 왜 안 나는가**: `ChatRoom.participants`가 `Set<ChatParticipant>`(`ChatRoom.java:27`)라 백(bag)이 아니다. 백은 `Member.role`(`List`) 하나뿐이므로 컬렉션 2개를 동시에 fetch join해도 걸리지 않는다. 만약 `participants`가 `List`였다면 이 방법은 막혔고, 그때의 대안이 `default_batch_fetch_size`다.
- **결과**: 2쿼리안이 실측 **2쿼리**로 확정 (설계 문서의 원래 목표 달성). general_log로 요청당 SQL 2건임을 직접 확인.

## 5. "실측 쿼리/요청"이란?

설계 문서의 시나리오표(N+1_성능테스트_설계.md 4-3장)에 있는 수치는 **코드를 보고 계산한 예상치**(예: before ≈ 2N+2)다. 반면 **"실측 쿼리/요청"은 실제로 요청을 날려서 MySQL 카운터로 잰 값**이다.

```
실측 쿼리/요청 = (측정 종료 시점 Com_select − 측정 시작 시점 Com_select) ÷ (요청 수 + warmup 수)
```

- `Com_select`: MySQL이 내부적으로 누적하는 SELECT 쿼리 실행 횟수 (`SHOW GLOBAL STATUS LIKE 'Com_select'`).
- `scripts/measure-n1.sh`가 `rooms.mjs` 실행 직전/직후에 이 값을 찍어 델타를 구하고, (요청 수 + warmup 수)로 나눈다 — warmup도 실제로 DB를 때리므로 분모에 포함해야 정확하다.
- 이 값이 "예상치"와 일치하는지 확인하는 것 자체가 검증이다. SQL 일반 로그(`mysql.general_log` 테이블, 6장)로 한 요청의 실제 쿼리 목록을 직접 세어봐도 같은 숫자가 나오는지 항상 교차 확인한다.

## 9. `participants` 빈 배열 버그 (해결됨)

- **증상(당시)**: 응답의 모든 방에서 `participants: []`. DB에는 방마다 참가자 2명이 있는데도 나오지 않음.
- **원인**: "내가 속한 방만 필터링"(`member.id.eq(loginId)`)과 "참가자 목록 fetch join"이 **같은 join을 재사용**했다. WHERE 조건이 그 join에도 적용되어, fetch join으로 채워지는 `participants` 컬렉션에 로그인 유저 자신만 담기고, 컨버터가 자기 자신을 필터링해 내보내니 결과가 항상 빈 배열이 됐다.
- **개선 전 코드가 정상이었던 이유**: 개선 전에는 `participants`를 lazy load로 별도 조회했기 때문에(그게 N+1의 원인 ②였음) WHERE 필터의 영향을 받지 않았다. 즉 **N+1을 없애다가 상대방 참가자 정보가 사라지는 회귀**였다.
- **해결**: 필터용 별칭과 fetch용 별칭을 분리했다.

```java
.join(chatRoom.participants, chatParticipant).fetchJoin()   // fetch 전용 — WHERE 조건 없음
.join(chatParticipant.member, member).fetchJoin()
.leftJoin(member.role).fetchJoin()
.join(meCp).on(meCp.chatRoom.eq(chatRoom)                   // 필터 전용 별칭
        .and(meCp.member.id.eq(loginId)))
.where(chatRoom.subject.id.eq(subjectId))
```

- **부수 효과**: WHERE에서 `chat_message` 정렬 조인을 뺄 수 있게 되어(정렬은 서비스 계층에서 마지막 메시지 시각으로 수행) 이슈 1의 MySQL 3065 원인 자체가 사라졌고, 조인 결과 행 수도 (참가자 × 메시지)로 불어나지 않는다.
- **검증**: 방 100개 시드 기준 `/rooms`·`/rooms/v2` 모두 `participants` 빈 방 0건, 상대방 멤버 정보 정상 반환.
