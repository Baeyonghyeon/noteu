# N+1 개선 — 면접 대비: "1쿼리안이 왜 더 느린가요?"

> [N+1_개선_설계.md](N+1_개선_설계.md) 5장(대안: 단일 쿼리)과 [성능테스트_결과.md](성능테스트_결과.md) 7장의 실측 결과를 면접에서 설명할 수 있도록 정리.
> 대상 질문: "방 목록 조회랑 마지막 메시지 조회를 하나의 쿼리로 합치면 더 안 좋나요? 라운드트립이 줄잖아요" / "이미 방이 특정됐는데(로그인 유저의 방 10개) 그 안에서만 조인하면 되는 거 아닌가요?"
> 작성: 2026-08-26

---

## 1. 한 줄 답변 (먼저 말할 결론)

> "라운드트립을 줄이는 이득보다, 자기 조인이 메시지를 한 건씩 비교하는 비용이 더 크기 때문입니다. 실제로 방이 적을 때(10개)는 1쿼리안이 더 빨랐고, 방/메시지가 많아질수록(100~200개) 2쿼리안이 역전해서 최대 2배 가까이 벌어지는 걸 실측으로 확인했습니다."

이 한 줄 다음에 "왜"를 SQL·실행계획(EXPLAIN)까지 근거로 풀어내는 게 이 문서의 목적.

---

## 2. 두 쿼리가 하는 일 — SQL 비교

### 2쿼리안 (채택안) — 방별 최신 메시지를 GROUP BY로 일괄 조회

```sql
SELECT id, room_id, message, ...
FROM chat_message
WHERE id IN (
    SELECT MAX(id) FROM chat_message WHERE room_id IN (10개 방 id...) GROUP BY room_id
)
```

- "방별 최대 id"를 **한 번의 집계**로 구하고, 그 id들로 필요한 행만 다시 조회.

### 1쿼리안 — 자기 조인(self-join)으로 "나보다 최신이 없는 메시지"만 필터링

```sql
SELECT chat_room.id, chat_message.*
FROM chat_room
JOIN chat_participant ...
JOIN member ...
LEFT JOIN chat_message  ON chat_message.room_id = chat_room.id
LEFT JOIN chat_message newer
       ON newer.room_id = chat_message.room_id
      AND chat_message.id < newer.id
WHERE chat_room.subject_id = ?
  AND member.id = ?              -- 로그인 유저 필터 → chat_room이 이미 10개로 좁혀짐
  AND newer.id IS NULL           -- "나보다 새 메시지가 없다" = 최신
```

- 방 목록과 마지막 메시지를 **한 번의 왕복**으로 가져오는 대신, `chat_message`를 자기 자신과 조인해서 "더 최신 메시지가 존재하지 않는 행"만 걸러낸다.

---

## 3. 자주 나오는 반론: "이미 방 10개로 좁혀졌는데, 그 안에서만 조인하면 되는 거 아닌가요?"

**이미 그렇게 되어 있다** — 라는 게 핵심 포인트. `LEFT JOIN chat_message ON chat_message.room_id = chat_room.id`에서 `chat_room`은 `WHERE ... member.id = ?`로 이미 로그인 유저의 방(10개)만 남은 상태이기 때문에, 이 조인은 처음부터 그 10개 방에 속한 메시지만 대상으로 한다. **다른 유저의 방까지 훑는 게 아니다.**

그런데도 느린 이유는 "범위"가 아니라 **"범위 안에서 처리하는 방식"**에 있다. 이걸 실행계획(EXPLAIN)으로 실측해서 확인했다.

---

## 4. 실행계획(EXPLAIN)으로 확인한 진짜 원인

방 50개 × 메시지 10개(총 500건) 데이터로 두 쿼리를 각각 `EXPLAIN` 떠본 결과:

```
1쿼리안 (자기 조인):
  chat_message(본인)   type=ALL   rows=500   Using join buffer (hash join)
  chat_message(newer)  type=ALL   rows=500   Range checked for each record ...; Not exists

2쿼리안 (GROUP BY):
  chat_message(최종조회) type=index rows=500  Using where; Using index   ← PK라 사실상 인덱스 룩업
  chat_message(서브쿼리) type=ALL   rows=500   Using where; Using temporary
```

핵심 차이:

| | 1쿼리안 (자기 조인) | 2쿼리안 (GROUP BY) |
|---|---|---|
| `chat_message` 처리 방식 | 전체를 훑은 뒤, **행 하나하나마다** "나보다 최신이 있나?"를 다시 비교(`Range checked for each record`) | `GROUP BY`로 **한 번의 집계**만에 방별 최댓값을 구함 |
| 최종 조회 | 없음 (조인 결과가 곧 최종) | 집계로 구한 id들을 **PK 인덱스로 바로 조회** (`type=index`, 빠름) |
| 비용이 비례하는 대상 | **메시지 총 건수** (행마다 재비교) | **방 개수** (집계 결과 크기) |

즉 "10개 방으로 범위를 좁히는 것"과 무관하게, 자기 조인은 그 범위 안의 **메시지 한 건 한 건마다 비교 연산이 붙는 구조**이고, GROUP BY는 **집계 1번으로 끝나는 구조**다. 방/메시지가 늘어날수록 이 차이가 벌어지는 게 당연한 결과.

> 덤으로 발견한 것: `chat_message`에 `room_id` 인덱스가 아예 없다(`PRIMARY(id)`뿐). 그래서 이 정도 데이터 규모에서는 두 방식 다 결국 테이블을 훑게 되는데, 그 안에서도 자기 조인 쪽이 "훑고 + 재비교"까지 하니 상대적으로 더 크게 손해를 본다. (인덱스를 추가하면 둘 다 빨라지겠지만, 자기 조인의 구조적 비효율 자체가 없어지는 건 아니다.)

## 5. 실측 수치와 연결

[성능테스트_결과.md](성능테스트_결과.md) 7-3장 결과:

| 방 수 | p95 ms (2쿼리안) | p95 ms (1쿼리안) | 비고 |
|---|---|---|---|
| 10 | 2.6 | **1.7** | 1쿼리안이 더 빠름 — 메시지가 적어 자기 조인 비용이 미미, 라운드트립 절감이 우세 |
| 50 | 4.8 | 4.9 | 거의 동률 (역전 지점) |
| 100 | **7.1** | 10.5 | 2쿼리안이 약 32% 빠름 |
| 200 | **12.7** | 26.4 | 2쿼리안이 약 52% 빠름 (2배 이상 격차) |

방 10개에서는 1쿼리안이 이겼다는 사실 자체가 중요한 포인트 — "무조건 쿼리 1개가 낫다"가 아니라 **데이터 규모에 따라 유불리가 바뀐다는 걸 실측으로 확인했다**는 서사가 된다.

## 6. 예상 후속 질문 & 답변 포인트

1. **"그럼 인덱스만 추가하면 1쿼리안이 이길 수도 있지 않나요?"**
   → 인덱스가 있으면 둘 다 빨라지지만, 자기 조인은 여전히 "행마다 재비교"하는 구조적 비용이 남는다(GROUP BY는 인덱스가 있으면 loose index scan으로 방 개수만큼만 훑을 수 있어 더 큰 이득을 봄). 구조적 차이는 인덱스로 완전히 사라지지 않는다 — 다만 이 부분은 실측하지 않았으므로 "추정"이라고 명확히 밝히고 답변.
2. **"라운드트립 1번 줄이는 게 그렇게 무의미한가요?"**
   → 무의미하지 않다. 방 10개(데이터가 적을 때)는 실제로 1쿼리안이 이겼다. "데이터가 적으면 라운드트립 절감이, 많으면 스캔 비용 감소가 더 크게 작용한다"는 트레이드오프로 설명.
3. **"프로덕션에서는 어느 쪽을 쓸 건가요?"**
   → 2쿼리안 채택. 이유는 (a) 방/메시지가 늘어나는 방향의 서비스라 확장성 있는 쪽이 안전, (b) 각 쿼리가 단순해서 유지보수·쿼리플랜 예측이 쉬움, (c) 실측 성능도 대부분의 구간에서 우세.
4. **"EXPLAIN을 어떻게 확인했나요?"** (재현 방법)
   ```bash
   docker exec noteu-mysql mysql -unoteu -pnoteu noteu -e "EXPLAIN SELECT ...;"
   docker exec noteu-mysql mysql -unoteu -pnoteu noteu -e "SHOW INDEX FROM chat_message;"
   ```
   → `type`, `rows`, `Extra` 컬럼(`Using join buffer`, `Range checked for each record`, `Using temporary` 등)을 보고 실행 방식을 해석했다고 설명.

---

## 7. 이 주제가 보여주는 것 (면접관에게 어필 포인트)

- "쿼리 개수가 적을수록 좋다"는 직관에 머무르지 않고, **실제로 두 안을 다 구현해서 A/B로 측정**했다.
- 결과가 예상과 다르게 나온 지점(방 10개에서 1쿼리안 승리)을 숨기지 않고, 오히려 **그 이유를 EXPLAIN까지 파고들어 설명**할 수 있다 — "왜"에 대한 답을 추측이 아니라 실행계획으로 검증했다는 게 핵심 신뢰 포인트.
- 이 과정에서 부수적으로 `chat_message.room_id`에 인덱스가 없다는 것도 발견 — 코드 밖의 스키마 이슈까지 확인하는 습관을 보여줄 수 있음.
