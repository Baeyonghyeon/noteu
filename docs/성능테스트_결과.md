# Short Polling vs SSE 성능 측정 결과

> 채팅 실시간 알림을 Short Polling → SSE로 전환했을 때의 서버 부하 차이를 검증하기 위한 A/B 부하 테스트 결과.
> 이력서 수치의 근거 자료로 사용. (2026-08-21 측정)

---

## 1. 테스트 개요

| 항목 | 값 |
|---|---|
| 측정 대상 | NOTEU 스프링 부트 서버 (Spring Boot 3.1.5, JDK 17) |
| DB | MySQL 8.4 (docker) |
| 환경 | 로컬 Mac + docker compose, 앱 컨테이너 **CPU 1코어 고정**(`cpus: 1.0`) |
| 시뮬레이션 사용자 | 10명 (로그인 세션 10개) |
| 시나리오당 시간 | 60초 |

### idle 가정 (중요)

- 이 테스트는 **idle 상태 100%** 를 가정한다: 사용자 10명 전원이 메시지를 보내지 않고,
  - 폴링: 채팅방 목록 REST API만 주기적으로 조회
  - SSE: 연결만 유지 (이벤트 수신 없음)
- 근거: 채팅 서비스에서 사용자 대부분의 시간은 "채팅방을 켜두고 아무것도 안 하는 상태"다.
  능동적 행동(메시지 전송, 방 생성)은 하루 중 극히 일부이며, 폴링은 **idle 상태에서도 요청이 계속 발생**하므로
  idle이 서버 부하의 대부분을 차지한다. 활성:비활성 비율이 1:9이든 0:10이든, 폴링 부하는 idle 유저의
  요청이 지배한다.
- 한계: 활성 유저가 섞인 혼합 시나리오(메시지 전송 포함)는 이번 측정에서 제외.

## 2. 측정 방법

### DB 조회 수
- MySQL의 `SHOW GLOBAL STATUS LIKE 'Com_select'` 누적 카운터(SELECT 쿼리 수)를
  시나리오 시작/종료 시점에 읽어 **델타 ÷ 60초 = 초당 DB 조회 요청 수** 산출.
- `Com_select`만 세므로 INSERT/UPDATE 등은 제외 — "DB 조회 부하"의 직접 지표.

### CPU / 메모리
- `docker stats --no-stream`을 **2초 간격으로 60초간 샘플링** (30회), 평균·최대값 산출.
- 앱 컨테이너를 1코어로 고정해 호스트 코어 수와 무관하게 비교 가능.

### 시나리오
| 구분 | 내용 |
|---|---|
| A. 폴링 | 10명 × **0.1초 간격**으로 `GET /subjects/1/chats/rooms` 호출 (실서비스 간격 0.1초 반영) |
| A'. 폴링(참고) | 10명 × 1초 간격 — 간격에 따른 선형성 확인용 |
| B. SSE | 10명이 `GET /sse` 연결 유지. 서버 30초 타임아웃으로 끊기면 자동 재연결 (브라우저 EventSource 동작 재현) |
| C. baseline | 무부하 |

부하 생성은 Node.js 스크립트(`load-gen/`) — 내장 fetch만 사용, 의존성 없음.

## 3. 측정 결과

### 3-1. DB 조회 (Com_select)

| 시나리오 | 요청 수 | DB 조회/초 | 비고 |
|---|---|---|---|
| A. 폴링 0.1초 | 5,940회 (99.0 req/s) | **406.0** | 방 8개 시드, 방당 쿼리 ~4.1개 |
| A'. 폴링 1초 | 590회 (9.8 req/s) | **40.3** | 0.1초의 1/10 — **선형성 확인** |
| B. SSE idle | 20회 (연결) | **0.25** | 사실상 0 |
| C. baseline | — | 0.02 | 측정 노이즈 |

### 3-2. CPU 사용률

| 시나리오 | 평균 | 최대 |
|---|---|---|
| A. 폴링 0.1초 | **19.33%** | 61.1% |
| A'. 폴링 1초 | **2.95%** | 10.3% |
| B. SSE idle | **0.49%** | 4.2% |
| C. baseline | **0.16%** | 0.2% |

### 3-3. 메모리 (컨테이너 RSS)

| 시나리오 | 평균 |
|---|---|
| A. 폴링 0.1초 | 504.9 MiB |
| B. SSE idle | 505.8 MiB |
| C. baseline | 505.6 MiB |

10명 수준에서는 SSE의 연결 유지 메모리가 ±1 MiB로 **무시 가능**.
단, SSE는 연결 수 × 객체 크기(emitter + emitterMap 엔트리)로 **선형 증가**하므로
동시 접속이 수천 명 수준이 되면 메모리 관리(emitter 제거 정책)가 필요해진다.
폴링은 세션 외에 연결 상태가 남지 않는다.

## 4. 해석

1. **DB 조회: 406/초 → 0.25/초 (99.9% 감소)** — 유휴 SSE 연결은 DB를 전혀 조회하지 않는다.
2. **CPU: 19.3% → 0.5% (97% 감소)** — SSE idle은 무부하(0.16%)와 사실상 동일.
3. **폴링 부하는 idle 유저가 만든다** — 0.1초 간격 10명의 부하가 전부 idle 유저의 요청.
   SSE는 idle 상태에서 서버에 거는 부하가 0에 수렴한다. 이것이 채팅 서비스에서 SSE 도입의 핵심 근거.
4. **CPU는 간격에 단순 비례하지 않는다** — 1초 → 0.1초(요청 10배)일 때 CPU는 2.95% → 19.33%
   (약 6.5배). 요청당 고정 비용(JSON 직렬화, JPA, DB 라운드트립, 로깅)이 지배적이므로
   CPU는 직접 측정해야 하며, 수학적 추정이 불가하다.

## 5. 이력서 교정안

### 기존 문구 (추정치)
> Short Polling 제거로 사용자 10명 기준 DB 조회 요청 초당 200회 → 0회,
> 서버 CPU 사용률 65% → 28% 감소

### 교정 문구 (측정 기반)
> Short Polling(0.1초 간격) 대비 SSE 도입으로, 사용자 10명 idle 기준
> **DB 조회 요청 초당 406회 → 0.25회 (99.9% 감소)**,
> **서버 CPU 사용률 97% 감소** (동일 환경 부하테스트 기준, 로컬 docker 1코어)

### 면접 대비 요약 (한 줄)
> 사용자 10명이 0.1초 간격으로 폴링하면 초당 406회의 DB 조회가 발생하는데,
> SSE로 전환하면 유휴 상태에서 초당 0.25회로 사실상 0이 되고, CPU는 19.3%에서 0.5%로 줄었습니다.
> 채팅 서비스는 idle 상태가 대부분이라, 폴링은 idle 유저의 요청이 부하의 대부분을 차지하지만
> SSE는 연결 유지에 드는 비용이 거의 없습니다.

### 한계 (먼저 말할 것)
- 로컬 환경 측정이므로 절대 CPU%는 배포 서버(EC2 등)와 다를 수 있음 → **감소율(상대값)** 기준으로 표기.
- idle 100% 가정 — 활성 유저가 섞인 시나리오는 미측정.
- 데이터 구성(방 수, 방당 쿼리 수)에 따라 절대값은 달라짐 (이번 시드: 방 8개, 방당 ~4.1쿼리).

## 6. 테스트 실행 방법

### 바로 실행 (서버가 이미 떠 있는 경우)

```bash
# 0.1초 간격 폴링 vs SSE idle vs baseline — 60초씩, 총 약 3분
./scripts/measure.sh 60 100
```

실행하면 시나리오별로 다음과 같이 출력된다:

```
=== 시나리오: A. 폴링 (10명 × 100ms 간격) (60s) ===
  DB 조회 요청/초      : 406.02
  CPU 평균             : 19.33%   (최대 61.1%)
  메모리 평균          : 504.9 MiB
=== 시나리오: B. SSE (10명 유휴 연결) (60s) ===
  DB 조회 요청/초      : 0.25
  CPU 평균             : 0.49%   (최대 4.18%)
...
```

### 처음부터 재현 (서버가 꺼져 있는 경우)

```bash
# 1. 서버 기동 (첫 빌드는 2~5분)
docker compose up --build -d

# 2. 앱 기동 대기: 로그에 "Started NoteuApplication"이 뜰 때까지
docker compose logs -f app

# 3. 테스트 유저 10명 생성 (비밀번호 1234)
./scripts/prepare-db.sh

# 4. 로그인 세션 10개 생성
node load-gen/login.mjs

# 5. 측정
./scripts/measure.sh 60 100
```

### 응용

| 하고 싶은 것 | 명령어 |
|---|---|
| 폴링 간격 바꿔서 측정 (예: 500ms) | `./scripts/measure.sh 60 500` |
| 폴링 부하만 직접 보고 싶을 때 | `node load-gen/polling.mjs 100 60` |
| SSE 연결만 유지해보기 | `node load-gen/sse.mjs 60` |
| 측정 시간 줄이기 (예: 20초) | `./scripts/measure.sh 20 100` |

### 주의사항

1. **앱을 재기동하면 DB가 초기화된다** (`ddl-auto: create` + data.sql 재시드).
   그 경우 3~4단계(prepare-db → login)를 다시 실행해야 한다. 세션만 죽은 경우에는 로그인만 다시 하면 된다.
2. **측정 중에는 앱을 재시작하거나 다른 부하를 섞지 말 것** — 각 시나리오가 60초 윈도우 안에서
   폐쇄적으로 측정되므로, 외부 부하가 들어오면 수치가 오염된다.
3. **재미있는 실험**: `./scripts/measure.sh 60 1000`(1초 간격)과 `60 100`(0.1초 간격)의 CPU를
   비교해 보면, 요청은 10배인데 CPU는 약 6.5배만 증가하는 것을 확인할 수 있다.
   이것이 "CPU 사용률은 요청 수로 단순 계산하면 안 되고 직접 측정해야 하는 이유"다.

## 7. N+1 개선 전/후 + 2쿼리안/1쿼리안 비교 (2026-08-26 측정)

> ⚠️ **이 장은 과거 기록이다.** 이후 `member_role` fetch join과 `participants` 버그 수정이 반영되어
> 채택안이 3쿼리 → **2쿼리**로 개선됐다. 또한 이 장의 p95는 표본 150요청이라 편차가 커서 신뢰도가 낮다.
> 최신·재측정 수치는 [8장](#8-membe_role-fetch-join--participants-수정-후-재측정-2026-09-03)을 볼 것.

> 배경: [N+1_개선_설계.md](N+1_개선_설계.md)의 N+1 제거 작업에서, 원본 코드(before)와 "2쿼리 전략"(채택안, `member_role` 이슈로 실측 3쿼리) · "1쿼리 전략"(자기 조인 대안, 실측 2쿼리)을 모두 실측 비교. 2쿼리안/1쿼리안은 별도 엔드포인트(`/rooms`, `/rooms/single`)로 구현해 동시에 비교했고, before는 관련 자바 소스만 `git stash`로 원본 커밋 상태로 되돌려 재빌드·측정한 뒤 다시 복구하는 방식으로 같은 환경에서 실측했다. 절차는 [N+1_검증_가이드.md](N+1_검증_가이드.md) 7장 참고.
> 환경은 1~6장과 동일(로컬 docker, 앱 컨테이너 1코어 고정).

### 7-1. 측정 방법

- 방 수(10/50/100/200)별로 `chat_message`/`chat_participant`/`chat_room`을 초기화 후 재시드(방당 메시지 10개), member 1(`aaaa`) 기준 순차 호출.
- 2쿼리안/1쿼리안: 요청 150회(warmup 20회 별도) × 3회 반복. before: 요청당 쿼리가 방 수에 비례해 늘어나 총 측정 시간이 길어지므로 요청 수를 40~100회로 줄여 3회 반복(방 수가 클수록 요청 수를 줄임 — N+1_성능테스트_설계.md 6장의 권장 사항).
- `avgMs`·`p95`는 3회 평균. 쿼리 수는 `Com_select` 델타 방식(5장 참고) — 회차 간 편차 없이 동일한 정수로 재현됨.

### 7-2. Before(원본 N+1) vs After(2쿼리안, 채택안)

| 방 수 | 쿼리/요청 (before) | 쿼리/요청 (after) | 쿼리 감소 | p95 ms (before) | p95 ms (after) | p95 개선율 |
|---|---|---|---|---|---|---|
| 10 | 22.0 | 3.0 | 86% (7.3배) | 29.7 | 2.6 | 91% |
| 50 | 102.0 | 3.0 | 97% (34배) | 26.3 | 4.8 | 82% |
| 100 | 202.0 | 3.0 | 99% (67배) | 31.0 | 7.1 | 77% |
| 200 | 402.0 | 3.0 | 99% (134배) | 78.3 | 12.7 | 84% |

- 쿼리 수는 `2N+2` 공식과 4개 시나리오 모두 정확히 일치(로그 관측 재확인 — 방 10개 22, 방 100개 202, 방 200개 402).
- **방 100개 기준: 요청당 쿼리 202회 → 3회(약 67배 감소), p95 응답시간 약 31ms → 7ms(약 77% 단축)**.
- 방 10개 구간은 요청 수가 상대적으로 적어(100회) before p95 편차가 컸음(3회차: 30.5/43.9/14.7ms) — 방 50 이상 구간이 더 안정적으로 재현됨.

### 7-3. 2쿼리안 vs 1쿼리안

| 방 수 | 쿼리/요청 (2쿼리안) | 쿼리/요청 (1쿼리안) | avg ms (2쿼리안) | avg ms (1쿼리안) | p95 ms (2쿼리안) | p95 ms (1쿼리안) |
|---|---|---|---|---|---|---|
| 10 | 3.0 | 2.0 | 1.9 | 1.4 | 2.6 | 1.7 |
| 50 | 3.0 | 2.0 | 4.1 | 4.4 | 4.8 | 4.9 |
| 100 | 3.0 | 2.0 | 6.1 | 9.7 | 7.1 | 10.5 |
| 200 | 3.0 | 2.0 | 11.4 | 25.4 | 12.7 | 26.4 |

### 7-4. 해석

1. **N+1 제거 효과가 명확함** — before는 쿼리 수가 방 수에 선형 비례(`2N+2`)해 방 200개에서 p95 78ms까지 늘어나지만, 두 개선안 모두 방 수와 무관한 상수 쿼리로 고정되어 방 200개에서도 p95 13~26ms 수준.
2. **2쿼리안 vs 1쿼리안은 방 수가 작을 땐 거의 동률, 커질수록 2쿼리안이 유리**:
   - 방 10개: 1쿼리안이 오히려 더 빠름 (라운드트립 1회 절감 효과가 지배적).
   - 방 100개: 2쿼리안 p95 7.1ms vs 1쿼리안 10.5ms (2쿼리안이 약 32% 빠름).
   - 방 200개: 2쿼리안 p95 12.7ms vs 1쿼리안 26.4ms (2쿼리안이 약 52% 빠름, 격차 2배 이상).
3. **설계 문서 5장의 사전 분석과 일치**: 1쿼리안(자기 조인)은 `chat_message` 테이블을 **자기 자신과 조인해 2회 스캔**하는 구조라, 메시지 수가 늘어날수록(방 수에 비례해 함께 증가) 스캔 비용이 커진다. 반면 2쿼리안은 단순 인덱스 조회 2회(목록 + `IN` 절 일괄 조회)라 방 수 증가에 상대적으로 덜 민감하다.
4. **결론**: N+1 제거만으로도 방 100개 기준 쿼리 67배 감소·응답시간 77% 단축이라는 큰 효과가 있고, 그 안에서 2쿼리안이 유지보수성뿐 아니라 방 수가 커질수록 성능에서도 우위라는 것이 실측으로 확인됨.

### 7-5. 한계

- 응답의 `participants` 필드가 개선 후 두 엔드포인트 모두 항상 빈 배열로 나오는 알려진 버그가 있는 상태에서 측정됨([N+1_검증_가이드.md](N+1_검증_가이드.md) 9장) — before 코드는 이 버그가 없어(참가자 정상 반환) before/after 간 응답 바디 크기·직렬화 비용이 완전히 동일하지는 않음. 다만 참가자 수가 방당 1~2명 수준이라 응답 크기 차이는 미미해 p95 비교에 미치는 영향은 작을 것으로 판단.
- before 측정은 방 수가 클수록 요청 수를 줄였다(200개 요청 40회) — 표본이 after(150회)보다 적어 신뢰구간이 다소 넓음. 다만 3회 반복 결과가 방 50 이상에서는 편차 ±10% 이내로 안정적이었음.
- 로컬 docker 1코어 환경 — 절대 ms 값보다 **격차의 방향과 배율**을 근거로 삼을 것.

## 8. `member_role` fetch join + `participants` 수정 후 재측정 (2026-09-03)

> 7장 이후 두 가지가 바뀌었다: (1) `member.role`을 fetch join해 3번째 쿼리를 제거, (2) 필터용/fetch용 조인 별칭을 분리해
> `participants` 빈 배열 회귀(7-5 한계에 적혀 있던 그 버그)를 해소. 즉 **이제 before와 after의 응답 바디가 동일**하므로
> 7장에 있던 "응답 크기가 완전히 같지는 않다"는 단서가 사라졌다.
> 아울러 7장보다 표본을 3배 이상 키워 p95 신뢰도를 높였다.

### 8-1. 측정 조건

- 방 100개 × 방당 메시지 10개, member 1(`aaaa`) 기준.
- **요청 500회 × 3회 반복, warmup 200회** (7장은 150회 × 3, warmup 20 — p95가 불안정했다).
- 단일 세션 순차 호출(`load-gen/rooms.mjs`) — 동시성 효과를 배제하고 요청당 비용만 측정.
- **before/after 동일 설정**: `default_batch_fetch_size`를 끈 원본 조건에서 양쪽 측정.
  before는 chat 소스만 `git stash`로 원본 커밋 상태로 되돌려 재빌드.
- 측정 중에는 `docker exec`(쿼리 카운트용) 등 외부 부하를 섞지 않았다.

### 8-2. 결과 (방 100개)

| 구분 | 쿼리/요청 | avg | p50 | **p95** | max |
|---|---|---|---|---|---|
| before (원본 코드) | **202.0** | 28.2ms | 28.0ms | **29.6ms** | 32~35ms |
| after · 채택안 `/rooms` | **2.0** | 4.4ms | 4.1ms | **5.6ms** | 21~42ms |

3회 반복 원값:

```
before : p95 29.8 / 29.5 / 29.4     (avg 28.3 / 28.1 / 28.1)
after  : p95  6.3 /  5.3 /  5.3     (avg  5.1 /  4.1 /  4.0)
```

- **방 100개 기준: 요청당 쿼리 202회 → 2회(101배 감소), p95 약 29.6ms → 5.6ms(약 81% 단축).**
- `202 = 2N + 2` 공식과 정확히 일치(재현 확인). after의 2.0도 반복 간 편차 없이 동일.
- after는 `default_batch_fetch_size`를 켠 상태(p95 6.3/5.3/5.3)와 끈 상태(5.7/5.2/6.1)에서 같은 값이 나왔다 —
  `/rooms`는 모든 컬렉션을 fetch join하므로 이 설정의 영향을 받지 않는다.

### 8-3. 분포의 비대칭 — before가 오히려 더 안정적이다

before는 p50 28.0 / p95 29.6으로 분포가 촘촘한 반면, after는 p50 4.1 / p95 5.6 / max 42.3으로 꼬리가 길다.
202번의 예측 가능한 DB 왕복이 시간을 지배하는 before에서는 GC나 스케줄링 지터가 상대적으로 묻히지만,
4ms대로 내려온 after에서는 같은 크기의 지터가 그대로 배수로 드러나기 때문이다.

**측정 시 주의**: 컨테이너 재기동 직후나 warmup이 부족하면 after의 p95가 40~57ms로 튄다(JIT 미완료 + 1코어 제한).
7장의 값(p95 7.1ms)과 이 장의 초기 시도(4.6ms)가 서로 다른 것도 표본 크기와 워밍업 차이 때문이다.
**결론: 이 환경에서 after를 측정할 때는 warmup 200회 이상, 표본 500회 이상을 쓸 것.**

### 8-4. 왜 절대값이 이렇게 작은가 (숫자의 타당성)

응답 시간이 ms 단위인 것은 DB가 특별히 빨라서가 아니라 **데이터셋이 작아서**다. 근거:

| 확인 항목 | 값 |
|---|---|
| 앱 → DB 경로 | 앱 컨테이너에서 `jdbc:mysql://mysql:3306/noteu`, MySQL `processlist`에 커넥션 10개 ESTABLISHED |
| 매 요청 쿼리 발생 | 110요청 동안 `Com_select` 델타 221 → 요청당 2.01 (응답 캐싱이었다면 0에 수렴) |
| 데이터 규모 | `chat_room` 100, `chat_participant` 200, `chat_message` 1,000 — 전부 InnoDB 버퍼 풀에 상주, 디스크 I/O 0 |
| MySQL 내부 순수 쿼리 시간 | `SHOW PROFILES` 기준 **0.50ms + 0.35ms = 0.85ms** |
| 응답 본문 | HTTP 200, 27,581바이트, 방 100 / 참가자 100 / lastMessage 100, `errors: 0` |

즉 after의 4~6ms 중 DB는 1ms 미만이고 나머지는 Spring Security 필터 + JPA 하이드레이션 + JSON 직렬화다.
before의 28ms도 `202회 × 약 0.14ms 왕복`으로 일관되게 설명된다.

**한계로 명시할 것**: 데이터가 버퍼 풀에 다 들어가는 규모라 디스크 I/O가 배제돼 있다.
실서비스처럼 데이터가 커지면 N+1의 왕복 비용은 더 커지므로, 이 측정은 개선 효과를 **과소평가**하는 쪽에 가깝다.

### 8-5. 쿼리 수가 적다고 빠른 게 아니다 — v2 사례

`/rooms/v2`는 마지막 메시지를 `leftJoin ... on chatMessage.id = (select max(id) from chat_message where room_id = chatRoom.id)`로
목록 쿼리에 합쳐 **요청당 1쿼리**를 달성한다. 그런데 p95는 27.8ms로 채택안(5.6ms)보다 **5배 느리다**.

상관 서브쿼리가 방마다 한 번씩 평가되기 때문이다. 즉 SQL 문(statement) 수는 1이지만 내부 작업량은 방 수에 비례한다.
반면 채택안의 2번째 쿼리는 `id IN (select max(id) ... group by room_id)` 한 번으로 전체 방을 처리한다.

> **N+1 최적화의 목표는 "쿼리 개수 최소화"가 아니라 "총 작업량이 데이터 규모와 무관해지는 것"이다.**
> 쿼리 수만 보면 v2가 이겼지만 실제로는 채택안이 5배 빠르다. 7-4의 결론(2쿼리안 우위)이 다른 방식으로 재확인됐다.

### 8-6. 이력서 문구 (측정 기반)

> 채팅방 목록 조회의 N+1을 제거해 **요청당 DB 쿼리를 방 개수와 무관한 상수 2회로 고정**.
> 방 100개 기준 **202회 → 2회**, **p95 응답시간 29.6ms → 5.6ms (약 81% 단축)**.
> (로컬 docker MySQL 8.4, 앱 1코어 고정, 500요청 × 3회, warmup 200 기준)

### 8-7. 한계

- 로컬 docker 1코어 측정 — 절대 ms보다 **감소율**을 근거로 삼을 것.
- 데이터가 버퍼 풀에 상주하는 규모라 디스크 I/O가 배제됨 (8-4).
- 방 100개 단일 시나리오에서만 재측정했다. 7장의 방 10/50/200 구간은 이전(3쿼리) 코드 기준 수치다.
- 측정 스크립트는 `Com_select` 델타를 (요청 + warmup)으로 나눈다. `docker exec mysql` 접속마다
  `select @@version_comment` 1건이 함께 세어지지만 170회 이상으로 나눠지므로 영향은 무시할 수준이다.
  단, **요청 1건만 놓고 셀 때는 이 +1이 그대로 드러나므로** 단건 확인에는 general_log를 쓸 것.
