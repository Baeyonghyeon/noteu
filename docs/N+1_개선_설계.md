# 채팅방 목록 N+1 쿼리 개선 설계

> `findAllById`가 방마다 개별 쿼리를 실행하는 N+1 구조를 QueryDSL 일괄 조회로 개선하기 위한 설계 문서.
> 개선 전/후 성능 검증 방법은 [N+1_성능테스트_설계.md](N+1_성능테스트_설계.md) 참고.

---

## 1. 문제 정의

### 1-1. 현재 코드 흐름

`RestChatServiceImpl.java:50-65` (`findAllById`):

```java
List<ChatRoomResponseDto> chatRoomResponseDtos = chatRoomRepository.findAllBySubjectId(subjectId, loginId).stream() // 쿼리 1
        .map(chatRoom -> {
            ChatMessage lastMessage = chatMessageRepository.findFirstByRoomIdOrderByCreatedAtDesc(chatRoom.getId()) // 방마다 쿼리 1
                    .orElse(new ChatMessage(null, null, null, ""));
            return converter.chatRoomEntityToChatRoomDto(chatRoom, loginId, lastMessage);
        })
        .toList();
```

### 1-2. N+1이 발생하는 지점 (2곳)

| # | 유형 | 지점 | 코드 | 발생 쿼리 |
|---|---|---|---|---|
| ① | 수동 N+1 | 마지막 메시지 조회 | `RestChatServiceImpl.java:53` — 루프 안의 명시적 호출 | 방마다 `SELECT ... FROM chat_message WHERE room_id=? ORDER BY created_at DESC LIMIT 1` |
| ② | lazy load N+1 | 참가자 접근 | `ChatConverter.java:24` — `chatRoom.getParticipants()` | `ChatRoom.participants`는 `@OneToMany` LAZY(`ChatRoom.java:25-27`) → 방마다 참가자 조회 1회. `ChatParticipant.member`는 `@ManyToOne` **EAGER(JPA 기본값)** 라 별도 쿼리 없이 참가자 조회에 조인됨 (로그 관측 확인) |
| ③ | EAGER 추가 조회 | 과목 접근 | `ChatConverter.java:21` — `chatRoom.getSubject().getId()` | `ChatRoom.subject`는 `@ManyToOne` **EAGER** → 요청당 1회 추가 조회 (같은 과목은 1차 캐시 재사용 — 로그 관측 확인) |

> **N+1의 두 종류** — "N+1"이라는 용어는 **쿼리 수의 패턴**(목록 조회 1회 + 행마다 개별 조회 N회)을 가리키며, lazy load는 그 패턴을 만드는 **원인 중 하나**다.
>
> - **②는 교과서적 N+1**: JPA의 LAZY 연관관계를 컬렉션/프록시로 접근할 때 JPA가 내부적으로 일으킨다. 쿼리 호출이 코드에 보이지 않아 발견이 어렵다.
> - **①은 수동 N+1**: lazy load가 아니라 개발자가 루프 안에서 명시적으로 호출한 쿼리. 쿼리 수의 결과 패턴은 ②와 동일(1+N)하다.
> - 이 프로젝트는 두 종류가 한 API에 섞여 있는 케이스다. 원인이 달라도 결과 쿼리 수가 1+N이면 N+1 문제로 통칭한다.
> - ③은 lazy load의 반대(EAGER)지만, 개발자가 의도하지 않은 추가 쿼리를 만든다는 점에서 같은 문제군이다. JPA에서 `@ManyToOne`·`@OneToOne`은 기본이 EAGER라는 점이 함정.

### 1-3. 쿼리 흐름 (사용자가 방 N개 보유 시)

```
쿼리 1        : 방 목록 조회 (findAllBySubjectId)
쿼리 2        : subject 조회 (EAGER, 1차 캐시로 요청당 1회)          ← ③
쿼리 3~N+2    : 방마다 마지막 메시지 조회                             ← ①
쿼리 N+3~2N+2 : 방마다 참가자 컬렉션 lazy load (member는 EAGER 조인)  ← ②
─────────────────────────────
요청당 2N + 2 개 (방 수에 선형 증가)
```

- **로그 관측으로 확정 (2026-08-25, 방 10개)**: 목록 1 + subject 1 + 마지막 메시지 10 + 참가자 10 = **22개** (member/member_role은 EAGER라 참가자 조회에 조인되어 별도 쿼리 없음).
- 방 100개면 요청당 약 202개 — 응답 시간이 방 수에 비례해 느려진다.

### 1-4. 왜 이 구조가 됐나

- 방 목록 화면에 "마지막 메시지 내용 + 시각"이 필요한데, 이는 메시지 테이블의 최신 레코드다 → 방 조회 후 방마다 "최신 메시지가 뭐지?"를 다시 물어보는 구조.
- 참고로 방 목록 쿼리(`ChatRoomRepositoryCustomImpl.java:29`)는 이미 `leftJoin(chatMessage)`을 하지만 `select(chatRoom)`이라 **정렬에만 쓰이고** 메시지는 결과에서 버려진다. 조인은 해놓고 데이터는 못 받아오는 구조.

## 2. 설계 목표와 제약

| 항목 | 내용 |
|---|---|
| 목표 | 요청당 쿼리 수를 방 수와 **무관한 상수(2개)** 로 고정 |

| 제약 4 | 기존 코드 스타일 유지 — `QuerydslRepositorySupport` 기반 (`ChatRoomRepositoryCustomImpl`과 동일 패턴) |

## 3. "방당 최신 메시지 1건" 구하는 방법 비교

> 이 문제 유형은 SQL에서 **"그룹당 최신 1건 조회(greatest-n-per-group, n=1)"** 이라 불리는 표준 패턴이다.
> 일반적인 해법은 ① MAX + GROUP BY 조인, ② 상관 서브쿼리, ③ 자기 조인, ④ (MySQL 8) 윈도우 함수
> `ROW_NUMBER() OVER (PARTITION BY room_id ORDER BY id DESC) = 1` 네 가지.
> 이 중 ①은 FROM 절 서브쿼리가 필요하고 ④는 JPQL이 윈도우 함수를 지원하지 않아 사용할 수 없으므로,
> **JPQL/QueryDSL에서는 ②와 ③만 가능**하다.

### 패턴 A: 서브쿼리 (WHERE 절 — JPQL 허용)

```sql
WHERE chat_message.id IN (SELECT MAX(id) FROM chat_message GROUP BY room_id)
```

- "각 방의 최대 id" 집합을 한 번 구하고, 그 집합에 속하는 메시지만 조회.
- **id를 기준으로 하는 이유**: `createdAt`은 `LocalDateTime`이라 DB에 초 단위로 저장될 수 있어, 같은 초에 보낸 메시지 2건이 둘 다 "최신"이 되어 중복 발생. `id`는 auto-increment(`AuditingFields.java:23`)라 유일하고 삽입 순서를 보장 → `MAX(id)` = 진짜 마지막 메시지.

### 패턴 B: 자기 조인 ("나보다 최신이 없는 것"만 남김)

```sql
LEFT JOIN chat_message newer ON newer.room_id = m.room_id AND m.id < newer.id
WHERE newer.id IS NULL
```

- 같은 방에서 id가 더 큰 메시지를 조인하고, 조인에 실패한(null) 행 = 최신 메시지.

### 비교

| | 패턴 A (서브쿼리) | 패턴 B (자기 조인) |
|---|---|---|
| 가독성 | 높음 — "방별 최대 id" 의미가 직관적 | 낮음 — 동작을 머릿속으로 시뮬레이션해야 함 |
| 인덱스 사용 | room_id 인덱스 + MAX 집계 | 자기 조인 두 번 스캔 |
| 단일 쿼리로 방 목록에 붙일 때 | 조인 서브쿼리가 필요 (FROM 절 불가로 어려움) | leftJoin 조건으로 자연스럽게 결합 가능 |

**채택: 패턴 A** — 배치 조회(2쿼리 전략)에는 가독성이 좋은 서브쿼리가 적합. 패턴 B는 단일 쿼리 대안(5장)에서만 사용.

## 4. 채택 설계: 2쿼리 전략

```
쿼리 1 : 방 목록 + 참가자/멤버 (fetch join으로 ② 제거)
쿼리 2 : 모든 방의 마지막 메시지 일괄 조회 (① 제거)
─────────────────────────────
총 2개 — 방 수와 무관
```

### 4-1. 방 목록 쿼리에 fetch join 추가 (참가자 lazy load 제거)

`ChatRoomRepositoryCustomImpl.java` 수정:

```java
@Override
public List<ChatRoom> findAllBySubjectId(Long subjectId, Long loginId) {
    QChatRoom chatRoom = QChatRoom.chatRoom;
    QChatParticipant chatParticipant = QChatParticipant.chatParticipant;
    QMember member = QMember.member;
    QSubject subject = QSubject.subject;
    QChatMessage chatMessage = QChatMessage.chatMessage;

    return from(chatRoom)
            .join(chatRoom.subject, subject).fetchJoin()                // ③ EAGER subject 조회를 쿼리 1에 통합
            .join(chatRoom.participants, chatParticipant).fetchJoin()   // ② 참가자 컬렉션 즉시 로딩
            .join(chatParticipant.member, member).fetchJoin()           // member 즉시 로딩 (WHERE 필터 겸용)
            .leftJoin(chatMessage).on(chatRoom.id.eq(chatMessage.roomId)) // 정렬용 (기존 유지)
            .where(chatRoom.subject.id.eq(subjectId)
                    .and(member.id.eq(loginId)))
            .orderBy(chatMessage.createdAt.desc())
            .select(chatRoom)
            .distinct()   // fetch join 시 루트(방) 중복 방지
            .fetch();
}
```

- `fetchJoin`으로 컨버터가 접근하는 `participants`가 같은 쿼리에서 초기화되어 방마다의 lazy load 쿼리(②)가 사라진다.
- `subject`는 `@ManyToOne` **EAGER**라 요청마다 1회 추가 조회가 발생함을 로그로 확인했다(③) → fetch join으로 쿼리 1에 통합해야 "총 2개 고정"이 성립한다.
- 정렬용 `leftJoin(chatMessage)`은 그대로 유지 — 최근 메시지순 정렬 동작 불변 (빈 방은 MySQL DESC에서 NULL이 마지막 → 맨 아래).

### 4-2. 마지막 메시지 일괄 조회 (QueryDSL 신설)

`chat/repository/querydsl/ChatMessageRepositoryCustom.java` 신설:

```java
package com.noteu.noteu.chat.repository.querydsl;

import com.noteu.noteu.chat.entity.ChatMessage;

import java.util.List;

public interface ChatMessageRepositoryCustom {
    /** 방 목록의 "방당 최신 메시지"를 일괄 조회 — N+1 제거용 */
    List<ChatMessage> findLastMessagesByRoomIds(List<Long> roomIds);
}
```

`chat/repository/querydsl/impl/ChatMessageRepositoryCustomImpl.java` 신설:

```java
package com.noteu.noteu.chat.repository.querydsl.impl;

import com.noteu.noteu.chat.entity.ChatMessage;
import com.noteu.noteu.chat.entity.QChatMessage;
import com.noteu.noteu.chat.repository.querydsl.ChatMessageRepositoryCustom;
import com.querydsl.jpa.JPAExpressions;
import org.springframework.data.jpa.repository.support.QuerydslRepositorySupport;

import java.util.List;

public class ChatMessageRepositoryCustomImpl extends QuerydslRepositorySupport implements ChatMessageRepositoryCustom {

    public ChatMessageRepositoryCustomImpl() {
        super(ChatMessage.class);
    }

    @Override
    public List<ChatMessage> findLastMessagesByRoomIds(List<Long> roomIds) {
        QChatMessage chatMessage = QChatMessage.chatMessage;
        QChatMessage m2 = new QChatMessage("m2"); // 서브쿼리용 별칭

        return from(chatMessage)
                .where(chatMessage.id.in(
                        JPAExpressions
                                .select(m2.id.max())          // 방별 최대 id = 방별 마지막 메시지
                                .from(m2)
                                .where(m2.roomId.in(roomIds))
                                .groupBy(m2.roomId)))
                .fetch();
    }
}
```

- 서브쿼리 1번으로 "방별 최신 메시지 id 집합"을 구하고, 그 id에 해당하는 메시지를 한 번에 조회.
- 방 수와 무관하게 쿼리 1개.

`ChatMessageRepository.java` 수정:

### 4-3. 서비스 리팩터링

`RestChatServiceImpl.java` (`findAllById`) 수정:

```java
@Transactional(readOnly = true)
@Override
public ChatRoomInfoResponseDto findAllById(Long subjectId, Long loginId) {
    List<ChatRoom> chatRooms = chatRoomRepository.findAllBySubjectId(subjectId, loginId);   // 쿼리 1 (fetch join 포함)

    List<Long> roomIds = chatRooms.stream().map(ChatRoom::getId).toList();
    Map<Long, ChatMessage> lastMessageByRoomId = roomIds.isEmpty()
            ? Map.of()
            : chatMessageRepository.findLastMessagesByRoomIds(roomIds).stream()             // 쿼리 2 (일괄)
                    .collect(Collectors.toMap(ChatMessage::getRoomId, Function.identity()));

    List<ChatRoomResponseDto> chatRoomResponseDtos = chatRooms.stream()
            .map(chatRoom -> converter.chatRoomEntityToChatRoomDto(
                    chatRoom, loginId,
                    lastMessageByRoomId.getOrDefault(chatRoom.getId(),
                            new ChatMessage(null, null, null, ""))))   // 빈 방: 기존과 동일한 fallback
            .toList();

    return ChatRoomInfoResponseDto.builder()
            .chatRoomResponseDtos(chatRoomResponseDtos)
            .loginId(loginId)
            .build();
}
```

## 5. 대안: 단일 쿼리 (자기 조인 + projection)

방 목록과 마지막 메시지를 **쿼리 1개**로 끝내는 방법. 채택은 2쿼리 전략으로 했지만,
**3-way 성능 비교(before / 2쿼리안 / 1쿼리안)를 위해 함께 구현**해 측정으로 우위를 확인하기로 했다.
가장 단순한 형태는 생성자 projection이지만, 이대로는 참가자 lazy load가 남아 실측은 1+N이 된다 (아래 "진짜 1쿼리" 참고):

```java
public record ChatRoomLastMessageDto(ChatRoom chatRoom, ChatMessage lastMessage) {}

// ChatRoomRepositoryCustomImpl에 추가
QChatMessage newer = new QChatMessage("newer");
return from(chatRoom)
        .join(chatRoom.participants, chatParticipant)
        .join(chatParticipant.member, member)
        .leftJoin(chatMessage).on(chatRoom.id.eq(chatMessage.roomId))
        .leftJoin(newer).on(chatMessage.roomId.eq(newer.roomId)
                .and(chatMessage.id.lt(newer.id)))   // 패턴 B: "나보다 최신"을 조인
        .where(chatRoom.subject.id.eq(subjectId)
                .and(member.id.eq(loginId))
                .and(newer.id.isNull()))             // 최신만 생존
        .orderBy(chatMessage.createdAt.desc())
        .select(Projections.constructor(ChatRoomLastMessageDto.class, chatRoom, chatMessage))
        .fetch();
```

**기각 사유**:
1. **참가자 lazy load(②)가 그대로 남는다** — 컨버터가 `participants`에 접근하므로 결국 fetch join이 필요한데, constructor projection과 fetch join의 조합은 Hibernate 버전별 동작이 까다로워 검증 부담이 크다.
2. 방당 1행 보장, 빈 방 통과, 정렬이 한 쿼리에 모두 얽혀 **설명·검증 단위가 커진다**.
3. 2쿼리 전략은 각 쿼리의 역할이 분리되어 있어 "쿼리 수 2개 고정"이라는 결과도 똑같이 얻으면서 검증이 쉽다.

### "라운드트립 1회면 무조건 낫지 않나?" — 1쿼리 vs 2쿼리 비용 분석

> "네트워크 요청이 1번이면 무조건 낫다"는 직관은 **라운드트립 수가 비용의 일부일 뿐**이라는 점을 놓치기 쉽다.

| 비용 항목 | 2쿼리 전략 (채택) | 1쿼리 전략 (자기 조인) |
|---|---|---|
| 라운드트립 | 2회 | 1회 |
| 쿼리 형태 | 단순 인덱스 조회 × 2 (목록 + IN 일괄) | 메시지 테이블 **2회 스캔** + 방당 1행 보장 조건 |
| 표준성 | JPQL 표준 (WHERE 서브쿼리) | projection + fetchJoin 조합은 Hibernate 버전 의존 |
| 검증 난이도 | 낮음 | 높음 |

- **라운드트립 비용의 실제 규모**: 로컬 MySQL 기준 ~0.1ms, 원격 DB여도 수 ms 수준이다. 반면 자기 조인은 메시지 수에 비례해 스캔이 늘어나 **데이터가 커질수록 비싸진다**. 어느 쪽이 빠른지는 데이터 크기·인덱스·네트워크 지연에 따라 달라진다 → 추정이 아니라 **측정으로 판단할 문제** (성능 테스트의 역할).
- **2쿼리 형태는 JPA 생태계의 표준 패턴**: Hibernate가 공식 제공하는 N+1 해법인 `hibernate.default_batch_fetch_size`·`@BatchSize`가 정확히 "부모 1회 + 자식 IN 절 1회" 구조다. 임시방편이 아니라 프레임워크가 보증하는 방식.
- **결론**: 목표는 "쿼리 수 최소화"가 아니라 "요청당 총 비용 최소화". 쿼리 수 1을 위해 검증 부담과 Hibernate 의존성을 지는 것은 이 프로젝트 규모에서 지불할 이유가 없다고 판단했다.

### "진짜 1쿼리"로 구현하려면 — participants 함정

위의 생성자 projection 버전은 그대로 구현하면 **요청당 1쿼리가 되지 않는다** — 컨버터가 `participants`에 접근하는 순간 방마다 lazy load 쿼리가 나가 실측은 1 + N이 된다. 진짜 1쿼리가 되려면 참가자·과목까지 같은 쿼리의 fetch join에 담고, 결과를 Tuple로 받아 서비스에서 조립해야 한다:

```java
// 1쿼리 변형 — 자기 조인 + fetch join + Tuple (Hibernate 6.2+ 동작 확인 필요)
public List<Tuple> findAllWithLastMessage(Long subjectId, Long loginId) {
    QChatRoom chatRoom = QChatRoom.chatRoom;
    QChatParticipant chatParticipant = QChatParticipant.chatParticipant;
    QMember member = QMember.member;
    QSubject subject = QSubject.subject;
    QChatMessage chatMessage = QChatMessage.chatMessage;
    QChatMessage newer = new QChatMessage("newer");

    return from(chatRoom)
            .join(chatRoom.subject, subject).fetchJoin()
            .join(chatRoom.participants, chatParticipant).fetchJoin()
            .join(chatParticipant.member, member).fetchJoin()
            .leftJoin(chatMessage).on(chatRoom.id.eq(chatMessage.roomId))
            .leftJoin(newer).on(chatMessage.roomId.eq(newer.roomId)
                    .and(chatMessage.id.lt(newer.id)))   // 패턴 B: "나보다 최신"을 조인
            .where(chatRoom.subject.id.eq(subjectId)
                    .and(member.id.eq(loginId))
                    .and(newer.id.isNull()))             // 최신만 생존
            .orderBy(chatMessage.createdAt.desc())
            .select(chatRoom, chatMessage)               // Tuple로 둘 다 반환
            .fetch();
}
```

서비스에서는 참가자 fetch join 때문에 방당 행이 참가자 수만큼 중복되므로, 방 id 기준으로 중복을 제거하며 조립한다:

```java
Map<Long, ChatRoom> roomById = new LinkedHashMap<>();
Map<Long, ChatMessage> lastByRoomId = new HashMap<>();
rows.forEach(t -> {
    ChatRoom room = t.get(chatRoom);
    roomById.putIfAbsent(room.getId(), room);
    ChatMessage msg = t.get(chatMessage);
    if (msg != null) lastByRoomId.putIfAbsent(msg.getRoomId(), msg);
});
```

- **리스크**: fetch join + Tuple + 자기 조인이 한 쿼리에 얽히는 조합이라 Hibernate 버전에 따라 동작이 달라질 수 있다 → 구현 후 로그로 "요청당 정확히 1개"인지 반드시 확인한다 (이 확인 자체가 측정의 일부).
- 이 복잡도·리스크가 2쿼리 전략을 채택한 이유이자, 동시에 "어느 쪽이 빠른지는 측정으로 판단한다"의 대상이다.

→ 일단 2쿼리 전략을 채택하되, 1쿼리 변형을 함께 구현해 전/후 측정으로 실제 우위를 비교한다 (테스트 설계 참고).

## 8. 이력서 문구 (최종 — 테스트 완료 가정, 컬리나리 에피소드와 동일 포맷)

> - **채팅방 목록 조회 N+1 제거**
>     - **상황**
>         - 채팅방 목록 API에서 방마다 마지막 메시지·참가자 정보를 조회할 때 원인이 다른 두 종류의 N+1이 겹쳐 발생: ① 루프 안에서 방마다 마지막 메시지를 개별 쿼리로 조회(수동 N+1), ② 컨버터가 접근하는 참가자 컬렉션이 `@OneToMany` LAZY라 방마다 추가 조회가 발생(lazy load N+1)
>         - SQL 로깅과 MySQL `Com_select` 카운터로 교차 검증해 방 10개 기준 요청당 21회, 방 100개는 201회, 200개는 401회로 확인 — 방이 많을수록 API가 점점 느려지는 구조였음
>     - **행동**
>         - 방별 최신 메시지를 "id 최댓값 서브쿼리로 일괄 조회"하는 방식으로 바꿔 방 수만큼 반복되던 쿼리를 1개로 축소 — createdAt 대신 id를 최신 판별 기준으로 삼아 동일 초 전송 메시지의 중복 문제를 사전에 차단
>         - 참가자 조회는 fetch join으로 통합해 lazy load로 새던 쿼리 제거. 여기서 "쿼리를 아예 1개로 합치는" 자기 조인 대안도 직접 구현해 별도 엔드포인트로 A/B 벤치마크 — 방이 적을 땐 1쿼리안이 우세했지만 방/메시지 수가 늘수록 자기 조인의 스캔 비용이 라운드트립 절감분을 앞질러 역전되는 지점을 데이터로 확인하고, "쿼리 개수"가 아니라 실측 성능 기준으로 2쿼리안을 최종 채택
>     - **성과**
>         - 요청당 DB 쿼리를 방 수와 무관한 상수로 고정 (방 100개 기준 201회 → 3회, 약 67배 감소), p95 응답시간 31ms → 7ms (약 77% 단축, 동일 환경 부하테스트 기준, 상세는 [성능테스트_결과.md](성능테스트_결과.md) 7장)

### 면접 대비 요약 (한 줄)

> 채팅방 목록 API가 방마다 개별 쿼리를 날려 방 100개 기준 요청당 201회의 DB 조회가 발생했는데,
> 방별 최대 메시지 id 서브쿼리 일괄 조회와 참가자 fetch join으로 요청당 3회(방 수와 무관한 상수)로 고정해 쿼리 수를 약 67배 줄였고, p95 응답시간은 31ms에서 7ms로 77% 단축됐습니다.
> createdAt 대신 id를 최신 판별 기준으로 삼아 같은 초에 온 메시지의 중복 문제를 피했고,
> 자기 조인 기반 단일 쿼리 대안도 구현해 실측 비교했는데, 방 수가 커질수록 자기 조인의 스캔 비용이 라운드트립 절감분보다 커져(방 200개 기준 약 2배 느림) 2쿼리안 채택이 성능으로도 뒷받침됐습니다.

### 면접 예상 질문

1. "방별 최신 메시지를 왜 createdAt이 아니라 id로 찾았나요?" → 초 단위 저장 시 동일 시각 중복 문제 (3장)
2. "FROM 절 서브쿼리를 못 쓰는 걸 어떻게 우회했나요?" → WHERE 절 서브쿼리 vs 자기 조인 비교 (3장)
3. "fetch join은 왜 필요한가요?" → 컨버터가 participants에 접근해서 방마다 lazy load 쿼리가 나가던 ② 문제 (1-2)
4. "distinct는 왜 붙였나요?" → fetch join 시 루트 엔티티 중복 방지
5. "단일 쿼리로는 못 하나요? / 라운드트립 2번이면 손해 아닌가요?" → 실제로 자기 조인 단일 쿼리 버전을 구현해 방 수별로 실측 비교함. 방 10개처럼 데이터가 적을 땐 1쿼리안이 근소 우위였지만, 방 100개부터는 자기 조인의 2회 테이블 스캔 비용이 라운드트립 1회 절감분을 넘어서 2쿼리안이 더 빨랐음(방 200개 기준 약 2배) — "쿼리 수 최소화"가 아니라 "실측 기반 트레이드오프 판단"이 기준이었다고 설명 (5장, [성능테스트_결과.md](성능테스트_결과.md) 7장)
6. "왜 2쿼리가 아니라 3쿼리인가요?" → `Member.role`이 `@ElementCollection(EAGER)`라 fetch join 대상 QueryDSL `EnumPath` 생성자가 protected라 통합이 불가능했음(컴파일 에러로 확인). 방 수와 무관한 상수라 N+1의 본질은 해결된 상태로 판단해 롤백 (N+1_검증_가이드.md 3장)
